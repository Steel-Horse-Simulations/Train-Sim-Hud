SECTION 1: WHAT THIS PROJECT IS
================================================================================

A Windows desktop HUD companion app for Train Sim World 6, built on the game's
optional -HTTPAPI flag. The game exposes a local REST API at
http://127.0.0.1:31270 that returns live telemetry: speed, signals, gradient,
weather, current loco, location, etc.

The app is a Flask backend (app.py) serving HTML/JS/CSS pages that talk to it.
It can run two ways:
  - run.bat → pywebview (renders in a real native Windows window)
  - run_browser.bat → just starts Flask, opens a browser tab

The user plays the game, the HUD shows real-time data. The user also has a
separate, unrelated "TSW HUD" app (different project, not this one) whose
SQLite database this app can read to import timetable and train-class data.

IMPORTANT: The API key lives in a file called CommAPIKey.txt (or DTGCommKey.txt)
in the game's save folder. The app reads it automatically, never asks the user
to type it. The key goes in every request as a header: DTGCommKey: <key>.

Game API base URL: http://127.0.0.1:31270
Confirmed real endpoints used (verified against the real game):
  GET /list                           - lists all top-level nodes
  GET /list/<path>                    - lists children of a node
  GET /get/<path>                     - reads a value
  PATCH /set/<path>                   - sets a value (used for weather)
  GET /info/<path>                    - metadata about a node
The response shape for /get is: {"Result": "Success", "Values": {"ReturnValue": <value>}}
but field names vary per endpoint. Always check "Values" then scan keys.

SECTION 3: WHAT NOT TO BUILD (EXPLICIT EXCLUSIONS)
================================================================================

The following were built in the original project but are EXCLUDED. They were
all actually REMOVED in v7.37.0 (they had lingered in the tree for several
versions after this decision was made). Do not add them back.

3A. HTTPS / TLS SUPPORT
  - No certs/ folder
  - No HTTPS_SETUP.md
  - No get_ssl_context() function in app.py
  - No get_https_cert_status() function in app.py
  - No /api/https_cert_status route
  - No certificate status panel on the Setup page (index.html)
  - run_flask() should just call app.run() directly on HTTP always
  - The app always runs on plain HTTP. That is fine and intentional.

3B. PWA / TABLET HOME SCREEN APPS
  - No manifest-*.json files
  - No pages/icons/ folder or any icon PNG files
  - No pages/sw.js (Service Worker)
  - No pages/offline-db.js (IndexedDB layer)
  - No pages/sync-client.js (sync orchestrator)
  - No pages/install-prompt.js
  - No install.html page
  - No /api/sync/changes or /api/sync/push routes
  - No offline sync capability at all — the app is online-only
  - No <link rel="manifest"> tags on any page
  - timetables_browser.html uses direct PATCH calls to save edits (not any
    kind of sync queue). Done as of v7.37.0.
  - timetable_db.get_changes_since() / train_classes_db.get_changes_since()
    still exist but nothing calls them. They are kept only because they carry
    the keyset-pagination fix described in Section 9E — do not delete them,
    and do not take their presence as licence to rebuild sync.

3C. KNOWN TRAINS — DRIVEN TRAINS ONLY (IMPORTANT BEHAVIOUR CHANGE)
  This is a deliberate design decision, not an oversight.
  The Known Trains v2 pages (known_trains.html, known_trains_edit.html,
  known_trains_group.html) should ONLY show train classes where times_seen > 0.
  
  "times_seen" is the counter incremented by record_live_sighting() every time
  the Dashboard detects that loco via the real game API. A value of 0 means the
  entry came purely from a catalog import (the other app's database), and the
  user has never actually driven it.
  
  The Known Trains pages are specifically for trains the user has driven.
  The catalog import still runs in the background (to enrich data with
  thumbnails, speeds, livery info, etc.) but it should NOT surface new entries
  in Known Trains — only live-detection does that.
  
  IMPLEMENTED in v7.37.0 (this had been specified but never actually built —
  the filter was on variant_of_class_id/is_visible only):
  - list_train_classes(driven_only=True) adds WHERE times_seen > 0
  - needs_attention(driven_only=True) adds the same clause
  - /api/known_trains/list passes True to BOTH. They must always agree: a
    needs-attention row with no matching list row is an item the person is
    being nagged about but cannot open and fix.
  - Other callers (the group-members list on the Classes page) leave
    driven_only False and still see the whole catalog.

SECTION 4: GROUND RULES — FOLLOW THESE IN EVERY SESSION
================================================================================

4A. PREVIEW BEFORE CODE (never skip this)
  For any new UI element (new panel, new page, new gauge): build an HTML
  mockup first, screenshot/render it, get approval, THEN build for real.
  Deliver the actual .html preview file, not just a screenshot.
  Preview accent colour: roll from the 9 themes
  (purple, green, blue, amber, crimson, teal, rose, slate, rainbow),
  excluding 2-3 recently used. Purple is the live app's default theme.
  Never use purple for a preview, it will be confused with the real app.
  Fixed real-world colours (e.g. GSM-R radio) override the roll.

4B. NAVIGATION — NEVER HAND-BUILD THE NAV
  The nav is built at runtime from pages/registry.json by pages/nav.js. Every
  page with a topbar uses:
    <div class="topbar">
      <div class="brand"><strong>TSW Hud</strong> · <page subtitle></div>
      <div class="nav" id="navContainer"></div>
      <button class="exit-btn" onclick="exitApp()">Exit</button>
    </div>
    ... <script src="/pages/nav.js"></script>
  nav.js sorts by `order` and marks the current page active by URL match, so
  adding a page means ONE new entry in registry.json — never an edit to every
  HTML file. Do not hand-write <a> tags into a nav container.
  In registry.json today: Setup | Dashboard (Desktop) | Dashboard (Tablet) |
    Timetables | Map | Discovery | Real Weather | HUD Lab | Known Trains.
  KNOWN GAP, deliberately left alone: classes.html, groups.html,
  operators.html, customisation.html and timetable.html are NOT in
  registry.json and so have no nav link — they are reached by links from the
  Known Trains pages. Do not "fix" this without being asked.
  dashboard.html, dashboard_tablet.html, map.html and timetable.html have no
  nav bar at all, by design.

4C. VERSIONING CONVENTION
  MAJOR.MINOR.PATCH where:
  - MAJOR (x.0.0) = a brand new feature
  - MINOR (x.x.0) = an update/addition to an existing feature
  - PATCH (x.x.1) = pure bug fixes or cosmetic changes only
  Always bump APP_VERSION in app.py when shipping a real update.

4D. SHIPPING CHECKLIST (every release)
  1. python3 -m py_compile on every .py file
  2. node --check on every external .js file in pages/
  3. node --check on every inline <script> in every .html file
  4. python3 -c "import json; json.load(open(...))" on every .json file
  5. Load every page/route in a real running server (all 200)
  6. Bump APP_VERSION in app.py
  7. Update PROJECT_NOTES.md
  8. Zip as "TSW Hud"

4E. NEVER GUESS AT API SHAPES
  The game's CommAPI returns different shapes for different endpoints. Never
  invent a response shape or assume field names. Only use endpoint shapes that
  have been confirmed via a real capture. Known confirmed shapes are listed
  in Section 7.

4F. SCREENSHOTS ARE INTERNAL CHECKS ONLY
  Never deliver a PNG as the output to the user. Deliver the .html file.
  Screenshots are used by the AI to verify the render before delivering.

4G. DASHBOARD: DESKTOP AND TABLET ARE ALWAYS IDENTICAL
  dashboard.html and dashboard_tablet.html must always be kept in exact sync
  on all HUD behaviour. They share dashboard.js. Different layout, identical
  logic.

4H. TESTING REAL DATA PATHS
  Before shipping any feature, test it against a real running Flask server
  (not just compile checks). Use mocked API responses in Playwright for
  anything that needs live game data.

SECTION 6: DATABASE SCHEMAS
================================================================================

--- loco_profiles.db (loco_profiles.py) ---
Table: loco_profiles
  raw_object_class TEXT PRIMARY KEY   e.g. "RVM_CJP_BNSF_ES44C4_C"
  clean_name TEXT                     e.g. "Class 66", learned from IS_GetVehicleInfo
  max_speed_mph REAL                  user-set override
  suggested_max_speed_mph REAL        learned from formationMaxSpeed API field
  times_seen INTEGER DEFAULT 0
  first_seen_at TEXT
  last_seen_at TEXT
  panel_prefs_json TEXT               reserved for future per-class panel prefs

--- timetables.db (timetable_db.py) ---
Table: journeys
  id INTEGER PRIMARY KEY AUTOINCREMENT
  route_id INTEGER
  route_name TEXT
  current_service_name TEXT NOT NULL  (the original imported service name)
  display_name TEXT                   (user-editable friendly name)
  notes TEXT
  imported_at TEXT NOT NULL           ISO timestamp
  updated_at TEXT NOT NULL            ISO timestamp, updated on every edit

Table: journey_segments
  id, journey_id (FK→journeys CASCADE), source_timetable_id INTEGER NOT NULL,
  seq_order INTEGER NOT NULL, service_name TEXT, section_id INTEGER,
  start_time TEXT, duration TEXT, bound TEXT,
  conductor_compatible INTEGER, playable INTEGER,
  updated_at TEXT NOT NULL

Table: journey_stops
  id, journey_id (FK→journeys CASCADE), source_timetable_id INTEGER,
  stop_order INTEGER NOT NULL, location_name TEXT,
  arrival TEXT, departure TEXT, latitude REAL, longitude REAL,
  updated_at TEXT NOT NULL

EDITABLE (PATCH-safe) fields:
  journeys: display_name, notes
  segments: start_time, duration, bound, conductor_compatible, playable
  stops: location_name, arrival, departure, latitude, longitude

get_changes_since(since_timestamp, after_journey_id=0, limit=100):
  Returns (page_of_journeys, has_more). Paginated via integer id keyset.
  Each journey in the page includes its segments and stops embedded.

--- train_classes.db (train_classes_db.py) ---
Table: train_classes
  id INTEGER PRIMARY KEY AUTOINCREMENT
  source_id INTEGER UNIQUE             the other app's train_classes.id
  source_name TEXT NOT NULL            as discovered from the API/other app
  display_name TEXT                    user-editable
  livery_id TEXT                       used as "company/operator" in practice
  livery_name TEXT                     e.g. "ScotRail" for display
  typical_length_m REAL, typical_car_count INTEGER
  is_electric INTEGER, is_steam INTEGER, is_diesel INTEGER
  electrification_types TEXT           JSON array: ["25kv_ac_overhead", etc.]
  max_speed_kph REAL, max_speed_mph REAL   catalog-sourced reference values
  max_speed_override_mph REAL          user-set override (Known Trains v2)
  dial_max_override_mph REAL           separate dial max override
  max_power_kw REAL, manufacturer_name TEXT
  engine_description TEXT, type_description TEXT
  vehicle_category TEXT, thumbnail_path TEXT
  rail_vehicle_class TEXT, is_drivable INTEGER, powered_axle_count INTEGER
  is_uk INTEGER NOT NULL DEFAULT 0
  is_visible INTEGER NOT NULL DEFAULT 0
  times_seen INTEGER NOT NULL DEFAULT 0    ← KEY FIELD: >0 means driven
  notes TEXT
  imported_at TEXT NOT NULL, updated_at TEXT NOT NULL
  group_id INTEGER REFERENCES loco_groups ON DELETE SET NULL
  subclass_id INTEGER REFERENCES loco_subclasses ON DELETE SET NULL

Table: loco_groups
  id INTEGER PRIMARY KEY AUTOINCREMENT
  name TEXT NOT NULL UNIQUE
  default_max_speed_mph REAL
  default_dial_max_mph REAL
  hud_panels TEXT    JSON array e.g. ["speed", "ammeter"]
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL

Table: loco_subclasses
  id INTEGER PRIMARY KEY AUTOINCREMENT
  group_id INTEGER NOT NULL REFERENCES loco_groups ON DELETE CASCADE
  name TEXT NOT NULL
  max_speed_override_mph REAL
  dial_max_override_mph REAL
  created_at TEXT NOT NULL, updated_at TEXT NOT NULL
  UNIQUE(group_id, name)

KNOWN TRAINS: DRIVEN-ONLY FILTER (see Section 3C)
  All Known Trains v2 queries must add WHERE times_seen > 0.
  The Classes page's member list does NOT have this filter — it shows every
  catalog row assigned to that class.

Speed resolution order (resolve_speeds()):
  1. train_classes.max_speed_override_mph   (individual override)
  2. loco_subclasses.max_speed_override_mph (subclass override)
  3. loco_groups.default_max_speed_mph      (group default)
  4. train_classes.max_speed_mph            (catalog-sourced fallback)
  5. 100.0 mph hardcoded                    (last resort)
  Same chain independently for dial_max. Source label returned alongside value.

Completion status (compute_completion()):
  7 fields: display_name, livery_name, livery_id, group_id, subclass_id,
            power_set (any of is_steam/is_diesel/is_electric), thumbnail_path
  0%   → red   | 1-49% → amber | 50-99% → yellow | 100% → green

Power label (compute_power_label(is_steam, is_diesel, is_electric)):
  1 type  → "Steam" / "Diesel" / "Electric"
  2 types → "Bi-Mode (X + Y)"
  3 types → "Tri-Mode (Steam + Diesel + Electric)"

Migration safety: ALWAYS use ALTER TABLE to add new columns, never CREATE/DROP.
Check via PRAGMA table_info before altering. Idempotent: safe on every startup.

SECTION 7: CONFIRMED API ENDPOINTS (real game captures)
================================================================================

These have been verified against the real game. Do not add new ones without
real verification.

Speed (m/s, convert ×2.23694 for mph):
  GET /get/CurrentDrivableActor.Function.HUD_GetSpeed
  Response: {"Values": {"ReturnValue": <float_ms>}}

Speed limit (m/s, same conversion):
  GET /get/DriverAid.Data
  Response: {"Values": {"SpeedLimit": <float_ms>, "formationMaxSpeed": <float_ms>, ...}}
  (use _get_ci() case-insensitive helper for SpeedLimit, formationMaxSpeed)

Gradient (%):
  GET /get/DriverAid.Data  (same call as above, reuse)
  Field: "gradient" in Values

Loco identity:
  GET /get/CurrentDrivableActor.ObjectClass
  Response: {"Values": {"ObjectClass": "<string>"}} (field name can vary)
  
  GET /get/CurrentFormation/0.Function.IS_GetVehicleInfo
  Response: {"Values": {"Output": {"class_<HASH>": "<clean_name>", ...}}}
  Match the "class_" prefix (the hash changes between game builds).

Location (for map):
  GET /get/DriverAid.Data
  Fields: latitude, longitude, elevation (all floats)

Weather (write, all 0.0–1.0 floats except Temperature):
  PATCH /set/WeatherSystem.Temperature  (Celsius, any float)
  PATCH /set/WeatherSystem.Cloudiness
  PATCH /set/WeatherSystem.Precipitation
  PATCH /set/WeatherSystem.Wetness
  PATCH /set/WeatherSystem.GroundSnow
  PATCH /set/WeatherSystem.PiledSnow
  PATCH /set/WeatherSystem.FogDensity
  Body: {"Value": <float>}

Ammeter (raw Amps, divide by 1000 for kA):
  GET /get/CurrentDrivableActor.Function.HUD_GetAmmeter
  Response: {"Values": {"Amps": <float>}}
  Scale: 0-8 kA for a Class 66. Green zone ~3-5 kA, red zone ~6-8 kA.
  Needle sweep: -50° (0 kA) to +50° (8 kA) — hand-picked, verify vs real gauge.

Brake gauges (confirmed endpoints exist, psi scaling NOT YET CONFIRMED):
  GET /get/CurrentDrivableActor.Function.HUD_GetBrakeGauge_1
  GET /get/CurrentDrivableActor.Function.HUD_GetBrakeGauge_2
  Which is brake pipe, which is main reservoir: NOT YET DETERMINED.
  Use HUD Lab to watch both side-by-side during real driving to find out.

GSM-R radio (confirmed endpoints for BP_Class375-6_GSMR_Radio):
  PageData, get() each property during real registration/call.
  Visual design (Siemens cab replica, fixed real-world colours): approved,
  NOT YET BUILT. Blocked on: confirming value shapes during a real call.

SECTION 8: ALL API ROUTES (app.py)
================================================================================

STATIC / PAGES:
  GET /                          → index.html (Setup page)
  GET /images/train_classes/<fn> → serves from images/train_classes/
  GET /api/pages                 → serves registry.json (page list for nav)
  GET /api/gauges                → serves gauges_registry.json
  GET /pages/<filename>          → serves from pages/ directory

CONFIG:
  GET  /api/config               → {config_folder, api_base, theme, ...}
  POST /api/config               → save config fields
  GET  /api/theme                → {theme, themes:[...]}
  POST /api/theme                → {"theme": "..."} to switch

NETWORK / DIAGNOSTICS:
  GET  /api/network              → {lan_ips, server_port, ...}
  GET  /api/diagnostics          → version, uptime, key status
  POST /api/autodetect           → auto-find CommAPIKey.txt folder

GAME API PROXY (these forward to 127.0.0.1:31270 with the auth header):
  GET  /api/proxy/get/<path>     → proxies GET /get/<path> to game
  PATCH /api/proxy/set/<path>    → proxies PATCH /set/<path> to game
  GET  /api/proxy/raw/<path>     → raw proxy, no response parsing

DISCOVERY:
  GET  /api/discover             → crawl /info + /list from game root
  GET  /api/discover/text        → same as above, plain text output
  POST /api/discover/save        → save crawl result to file

LOCO / PROFILE:
  GET  /api/loco                 → {name, raw, max_speed_mph, ...}
  GET  /api/loco/profiles        → list all profiles from loco_profiles.db
  POST /api/loco/max_speed       → {"raw": "...", "mph": 90} to set custom max

LOCATION:
  GET  /api/location             → {latitude, longitude, elevation}

TIMETABLES:
  GET  /api/timetables           → {journeys:[...]} paginated, ?q= search
  GET  /api/timetables/<id>      → single journey with segments+stops embedded
  PATCH /api/timetables/<id>     → edit journey (display_name, notes only)
  PATCH /api/timetables/segments/<id> → edit segment (start_time, duration...)
  PATCH /api/timetables/stops/<id>    → edit stop (location_name, times...)

KNOWN TRAINS v2 (driven-only view of the catalog):
  NOTE: the old flat catalog page (train_classes.html) and its /api/train_classes
  routes NO LONGER EXIST. Everything goes through /api/known_trains/*.

  GET  /api/known_trains/list         → {classes:[...resolved...], needs_attention:[...]}
                                        Both lists filtered to times_seen > 0.
                                        Each class includes resolved speeds,
                                        completion status, power label,
                                        group_name, family_name, operator_colour.
  GET    /api/known_trains/classes/<id>  → single train class
  PATCH  /api/known_trains/classes/<id>  → edit (EDITABLE_FIELDS only)
  POST   /api/known_trains/restore       → restore a wiped/hidden entry
  POST   /api/known_trains/wipe_all      → clear the whole Known Trains set

CLASSES (API path still says "groups" — the PAGE is called Classes):
  GET    /api/known_trains/groups       → {groups:[...]}
  POST   /api/known_trains/groups       → create {name, default_max_speed_mph, ...}
  GET    /api/known_trains/groups/<id>  → class + subclasses + members
  PATCH  /api/known_trains/groups/<id>  → update
  DELETE /api/known_trains/groups/<id>  → delete
  POST   /api/known_trains/groups/<id>/subclasses → create subclass
  PATCH  /api/known_trains/subclasses/<id>        → update subclass
  DELETE /api/known_trains/subclasses/<id>        → delete subclass

GROUPS = FAMILIES (several Classes under one family name):
  GET    /api/known_trains/families       → {families:[...]}

9B. LIVE LOCO DETECTION
  Every Dashboard poll cycle calls find_loco_class(), which:
    1. GET /get/CurrentDrivableActor.ObjectClass → raw key
    2. GET /get/CurrentFormation/0.Function.IS_GetVehicleInfo → clean name
    3. GET /get/DriverAid.Data → formationMaxSpeed (m/s)
    4. Calls BOTH:
       loco_profiles.record_sighting(raw, clean_name, formation_max_speed_ms)
       train_classes_db.record_live_sighting(raw, clean_name, formation_max_speed_ms)
    5. Returns best available display name (clean > remembered > raw)

  record_live_sighting() in train_classes_db:
    - If name already exists in train_classes (any source): bumps times_seen
    - If name is new: creates a NEW row with source_id=NULL, times_seen=1,
      is_visible=1 immediately (always visible, the user just drove it)
    - If a later catalog import finds a matching name: RECONCILES (adopts the
      existing placeholder row, fills in thumbnail/speed/livery/etc) rather
      than creating a duplicate

9C. DASHBOARD POLLING (dashboard.js)
  Three independent poll cycles, all using the /api/proxy/get/ endpoint:
    - Speed: every 300ms via HUD_GetSpeed
    - DriverAid.Data: every 800ms (gradient, speed limit)
    - Weather: every 30s
  Also: pollLoco() every 5s via /api/loco
  
  Speed gauge SVG ring: circumference = 314 (r=50 circle), stroke-dasharray
  set proportionally to currentSpeedMph / dialMax. The ring is SPLIT: the
  normal segment runs up to max speed and is coloured by the current speed
  limit; a second segment covers only the portion PAST max speed, in red.

  ANALOGUE SPEEDOMETER — ANGLE CONVENTIONS. Read this before touching the
  gauge. Two long-lived bugs lived here and both came from getting it wrong.
    - The gauge SVG is rotated -90° BY CSS. Everything is authored in SVG
      space; that rotation does the final turn.
    - Value → SVG angle:  A = 224.5 + (v / dialMax) * 271, clockwise from
      east. Do not round 224.5 or 271 to tidier numbers — the geometry is a
      direct transcription of the approved mockup, scaled 50/460.
    - An element DRAWN POINTING UP (the needle, the max-speed tick) already
      sits at SVG 270. To place it at value v it needs rotate(A - 270).
      Using rotate(A) puts it 270° out — which reads as "stuck in the same
      place" rather than as an obvious rotation error.
    - polarPoint() must NOT subtract an extra 90. Doing so rotates the whole
      number ring a quarter turn.
    - Numbers in 10s; 5s when dialMax ≤ 50, with 1mph minor ticks.
    - The digital readout is a real 7-segment display (individual bars, ghost
      segments always drawn), 3 digits, no decimal point, bordered panel.
    - Digital mode is disabled app-wide but ALL its code is retained;
      pollLoco() forces setSpeedometerMode('analogue').

  Max-speed tick: SVG line, see the rotate(A - 270) rule above
  DIAL_HEADROOM_MULTIPLIER = 1.2 is a TEMPORARY placeholder.
  When Known Trains v2 is eventually rewired to the Dashboard, replace this
  with the real resolve_speeds() values from train_classes_db. The comment
  in dashboard.js marks this with "search for this comment" to make it easy
  to find.

9D. OTHER HUD SYNC BACKGROUND THREAD
  other_hud_sync.py runs a daemon thread on startup. It:
    - Scans common folders (Downloads, Desktop, Documents, etc.) for tsw_hud.db
    - Opens the found DB read-only (mode=ro in connection string)
    - Checks the row count before doing a full import (skip if unchanged)
    - Re-checks every 15 minutes
  Runs alongside import_from_other_hud.py which is the one-off CLI version.

9E. TIMETABLE DB: GET_CHANGES_SINCE PAGINATION
  get_changes_since(since, after_journey_id=0, limit=100):
    Step 1: Cheap - collect SET of journey ids where any row (journey,
            segment, or stop) has updated_at > since
    Step 2: Sort ids, slice with id > after_journey_id cursor, take limit+1
    Step 3: Fetch full nested objects for only that page
    Returns: (list_of_journeys_with_embedded_segments_and_stops, has_more_bool)
  
  train_classes_db uses the same pattern (same two-step collect+slice approach).
  Do NOT use a single SQL query mixing fixed since_timestamp with id cursor
  via OR — this was tried and had a real bug: when updated_at > since matches
  all rows (which it does on a full first-ever sync), the OR's id-cursor
  clause becomes completely ineffective, returning the first page forever.

SECTION 11: KNOWN TRAINS V2 DESIGN
================================================================================

TERMINOLOGY — READ THIS FIRST. The words changed; the API paths did not.
  Family  ("Group" in the UI, groups.html, /api/known_trains/families)
    e.g. "Class 8xx" — several Classes belong to one Family.
  Class   ("Class" in the UI, classes.html, /api/known_trains/groups)
    e.g. "Class 801" — this is the table still called loco_groups.
  Subclass — within a Class, /api/known_trains/subclasses
  Entry   — an individual train_classes row, edited on known_trains_edit.html
So: Family → Class → Subclass → Entry. Where this spec's older text says
"group" against an API path, it means CLASS. This mismatch is deliberate —
renaming the endpoints was judged not worth the churn.

KNOWN TRAINS LIST (known_trains.html):
  - Fetches /api/known_trains/list (which applies times_seen > 0 filter)
  - Groups entries by family_name when the class has a family, else by the
    class name (ungrouped → "(Ungrouped)" bucket)
  - Pills: 156px tall, 420px thumbnail, full width, image on the RIGHT
  - Pill colour comes from the LIVERY, not the operator. The server resolves
    it per train (operator_colour in /api/known_trains/list) — livery colour
    first, operator colour as fallback. Pill background is that colour at 20%.
  - The curved coloured edge is a SOLID layer (.pill-wrap background) with the
    inner pill's border-radius carving the concave curve, and a mask-image
    (opacity only) fading it out to the left. Do NOT rebuild this as a
    gradient with a colour stop — a stop makes a square edge no radius fixes.
  - Operator logo is looked up by the operator's short_code:
    /company_logos/<short_code>.png. There is no logo_path field.
  - Needs Attention section: entries below 100% completion, same driven-only
    filter as the list. Auto-hides if empty.
  - "Set up" button links to the edit page, class settings link per group

KNOWN TRAINS EDIT (known_trains_edit.html):
  - Two-column grid: left = photo slot + field completion checklist; right = form
  - Source name shown read-only (API raw string)
  - Identity: display_name, livery_name, livery_id (label: "Company / operator")
  - Grouping: Class dropdown (fetches /api/known_trains/groups), then
    Subclass dropdown (refetches class detail when the class changes)
  - Variants panel: attach another train as a variant of this one. Wholly
    non-destructive and reversible — the row is tagged variant_of_class_id,
    disappears from Known Trains, and comes back intact when detached. The
    variant dropdown offers only UNGROUPED trains. Display name and
    speedometer values resolve to the PARENT.
  - Speeds: two inputs (max train speed, dial max). Caption shows whether
    value is "custom for this train" vs "using group/subclass default".
    Reset link restores the inherited default. The inherited default is
    computed client-side from the selected group/subclass data.
  - Power: Steam/Diesel/Electric checkboxes as styled "power chip" pills.
    Electric checkbox reveals electrification sub-options (25kV AC overhead,
    750V DC third rail, 630V DC fourth rail). Live Bi-Mode/Tri-Mode badge.
  - HUD panels: read-only note linking to class settings
  - Field completion sidebar updates live as form fields change
  - Status dot (red/amber/yellow/green) updates live
  - Save → PATCH /api/known_trains/classes/<id> → redirect to list

COMPLETION FIELDS: display name, operator, livery, class, power.
  NOT subclass, and NOT photo. This was corrected explicitly — do not add
  either back into the completion calculation.

OPERATORS (operators.html):
  - Operators each have a name, short_code (used for the logo filename) and a
    default colour, plus a list of liveries each with their own code, name and
    colour. On a train row, livery_id holds the OPERATOR id and livery_name
    holds the LIVERY code — legacy column names, do not "fix" by renaming.

GROUPS / FAMILIES (groups.html):
  - Backed by the class_families table and family_id on loco_groups.
  - A Family is purely a display grouping for the Known Trains list; it
    carries no speed defaults of its own.

CLASS SETTINGS (known_trains_group.html — the page is titled "Class"):
  - Class name (editable, saves on blur)
  - Default max speed + dial max (save on change)
  - Subclasses list with inline speed override inputs (save on change)
  - Add subclass form (slide-in, name required, speed optional)
  - HUD panel toggles per-gauge (persisted as hud_panels JSON array)
    Speed gauge: always on, shown as disabled/greyed
    Other gauges: toggleable, stored even if the gauge isn't built yet
  - Members of this class (linked to their edit pages). This list is NOT
    driven-only — it shows every catalog row assigned to the class.

SPEED CAPTIONS (client-side, on the edit page):
  "Using <source> default (<value>) — change to override just this train"
  "Custom for this train — <source> default is <value> [Reset to <value>]"
  <source> is "group <Name>" or "subclass <Name>" or "catalog data"
